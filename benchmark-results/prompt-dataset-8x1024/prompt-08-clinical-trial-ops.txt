一家多中心临床试验正在评估一种用于罕见病的口服药物。试验覆盖 14 个国家、86 家医院和 2,400 名受试者，数据来源包括电子病例、实验室结果、药物发放记录、可穿戴设备和患者报告。运营团队最近发现，部分中心的随访时间戳晚于实验室采样时间，另一些中心把停药原因写在自由文本而不是受控词表中。数据管理委员会要求在不改变原始记录的情况下完成清理，并在下一次 interim analysis 前冻结一个可审计的数据快照。

问题最早出现在北欧的三个中心。受试者在第 28 天完成访视，但实验室系统在第 29 天才上传结果；ETL 任务按照上传时间排序，于是模型把部分结果误认为第 29 天访视。与此同时，药物发放系统有一次时区配置错误，把本地夏令时转换成 UTC 时多减了一个小时。单个记录看起来只是几分钟差异，但当它与用药依从性、生命体征和不良事件窗口结合时，会改变 protocol deviation 的分类。

运营团队保留了 source database、ETL job log、数据字典、中心培训记录和审计轨迹。任何修订都必须有 reason code、操作者、时间戳和原值/新值。分析数据库中的派生字段不能覆盖 source；它们需要与版本化 transformation code 绑定。为了减少重复计算，团队考虑把常用的 patient timeline 缓存到 host DRAM，把等待 GPU 批处理的特征张量放入 pinned staging，但缓存中绝不能留下可重新识别的姓名、住址或自由文本原文。

隐私和性能约束必须同时满足。主机内存加密由节点级机制提供，但调试 profile 仍可能记录专家 id、批次大小和访问次数。日志系统不能打印完整 prompt 或 patient identifier，只能使用不可逆 subject key。page cache 可能把包含敏感字段的文件页留在内存中，因此清理策略需要按照文件用途和保留期限设计。物理 SSD read、逻辑文件读取和 DRAM cache hit 也必须分别记录，以免性能报告误导安全评审。

数据冻结流程分为四步。第一步锁定 extract cutoff，禁止新的 source record 进入快照；第二步运行 schema validator，检查单位、范围、时区和 controlled vocabulary；第三步由医学审阅者处理高风险不一致；第四步生成 immutable manifest 和 hash，并把每个 derived table 的输入版本写入 manifest。任何 GPU 加速的 join 或缺失值填充都要与 CPU reference 结果对比，最大绝对误差和行级 digest 都要记录。

测试场景不能只使用一批平均患者。需要覆盖高频随访、长时间缺测、多个时区、药物批次切换、中心迁移、严重不良事件和撤回同意。每个场景使用一条独立自然上下文，模式之间严格配对；三次运行可用于观察系统噪声，但不能把不同场景当成同一个 prompt 的重复。对于任何结果差异，先检查 tokenization、route trace、cache tier 和数据快照版本，再讨论性能。

委员会最终要看到一份同时面向工程和医学读者的报告。报告应给出数据完整性结论、隐私风险、冻结快照 hash、处理吞吐、p95/p99 延迟、主机内存峰值、GPU H2D 时间和异常重试次数。若 pinned upper bound 只略快于普通 host cache，应优先选择更易审计的 pageable 方案；若缓存导致审计字段丢失，即使平均吞吐提高，也不能进入临床环境。
统计团队还要处理缺失数据机制。实验室结果缺失可能来自真实未采样、设备故障或上传延迟，三者不能用同一个默认值填补。派生特征必须保存 missingness reason 和 imputation version，模型输出也要能追溯到这两个字段。缓存命中不能跳过 freshness 检查，尤其是安全性事件和停药记录。

多中心回放将按国家、中心、访视阶段和事件严重程度分层抽样。每层至少保留一个长缺测窗口、一个跨时区窗口和一个药物批次切换窗口。模式之间必须读取同一份脱敏快照，且 prompt_id、snapshot_hash、route_trace 和输出 digest 都进入结果表。三次运行的顺序采用拉丁方，避免某种模式总是在高温或高负载时执行。

审计委员会还要求测试异常恢复：在 host cache preload 完成一半时终止进程，在一次 H2D 传输等待期间触发取消，再从同一 manifest 重新启动。恢复后不能留下旧版本的患者特征，也不能把半完成的缓存条目标记为 READY。只有资源释放、数据清理、数值一致性和性能四项都通过，缓存方案才可以用于真实临床工作流。
数据管理者还会检查重复访视、撤回同意后的记录和跨系统 subject mapping。重复记录不能简单取最后一条，因为医学审阅可能已经对较早记录做过确认；撤回同意后的数据要按照批准的保留政策处理；subject mapping 必须在脱敏边界内完成。所有这些规则都应在 prompt 所描述的场景中留下可验证的证据，而不是只写成报告里的概念。

性能实验在每个快照上保存 input manifest、输出 digest 和异常清单。若 host cache 命中减少了文件读取，却改变了缺失值填补顺序，结果应标记为 correctness failure。只有 token、route、数值误差、隐私字段和资源释放全部通过，才可以把该场景的吞吐纳入跨 prompt 汇总。
